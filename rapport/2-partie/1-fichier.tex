\section*{Introduction}
Ce chapitre présente le contexte du projet, l'analyse des besoins, l'étude de l'existant, la méthodologie et la conception de l'architecture agentique. Nous y formalisons les difficultés rencontrées, les besoins fonctionnels et non fonctionnels, les contraintes techniques, puis nous détaillons l'architecture générale, la base de données et les workflows agents.

\section{Présentation du projet}
Ce projet de fin d'études s'inscrit dans le cadre de la refonte du Système d'Information (SI) Commercial d'un opérateur télécom, plus précisément autour du système \textbf{CCU} (Commande et Catalogue Unifiés). L'objectif est de concevoir et de développer un \textbf{agent IA de diagnostic technique} capable d'assister les équipes de support dans la résolution des incidents affectant ce SI.

\subsection{Contexte}
Dans un secteur des télécommunications en constante mutation, les opérateurs doivent moderniser leur SI Commercial pour répondre aux attentes des clients et soutenir le déploiement de nouvelles technologies (FTTH, 4G/5G). Le programme de refonte porte sur le système \textbf{CCU}, qui centralise le catalogue de produits et la gestion des commandes clients.

Le projet objet de ce mémoire ne porte pas sur la migration de données, mais sur la conception d'un agent IA de diagnostic technique capable d'assister les équipes de support. L'agent exploite les APIs \textbf{TMF620} (Product Catalog) et \textbf{TMF622} (Product Ordering) du TM Forum pour s'aligner sur les standards de l'industrie télécom.

\subsection{Problématique}
Les équipes de support technique font face à des incidents dont l'investigation requiert de consulter plusieurs sources disjointes :

\begin{itemize}
    \setlength\itemsep{0.1em}
    \setlength\parskip{0pt}
    \setlength\parsep{0pt}
    \item Les \textbf{logs réseau} et applicatifs, souvent volumineux et difficiles à interpréter rapidement.
    \item Le \textbf{contexte client} stocké dans le CRM (statut du contrat, services actifs, historique).
    \item Les \textbf{tickets historiques} résolus, qui contiennent une expertise précieuse mais sont difficiles à exploiter manuellement.
\end{itemize}

Cette dispersion des données engendre des temps de diagnostic longs, une dépendance forte à l'expertise humaine et un risque d'erreur. La problématique centrale est donc la suivante : \textbf{comment concevoir un système intelligent capable de corréler automatiquement ces sources pour produire un diagnostic fiable, explicable et actionnable, sans jamais exécuter d'action corrective automatique sur le SI réel ?}

\subsection{Objectifs}
Les objectifs du projet se déclinent en quatre axes :

\begin{itemize}
    \setlength\itemsep{0.1em}
    \setlength\parskip{0pt}
    \setlength\parsep{0pt}
    \item \textbf{Centraliser l'investigation} : offrir un point d'entrée unique qui agrège les sources pertinentes à un incident.
    \item \textbf{Fiabiliser le diagnostic} : réduire les erreurs humaines grâce à une corrélation structurée et à un raisonnement guidé par les données.
    \item \textbf{Capitaliser l'expertise} : exploiter les tickets historiques via un graphe de connaissances et une recherche sémantique.
    \item \textbf{Garantir la sécurité} : s'assurer qu'aucune action technique n'est exécutée automatiquement et que les données sensibles sont filtrées.
\end{itemize}

\section{Analyse des besoins et étude de l'existant}

\subsection{Difficultés rencontrées dans les projets}
Les projets de support et de maintenance du SI CCU rencontrent plusieurs difficultés récurrentes.

\paragraph{Fragmentation des sources de données :}
Les informations pertinentes à un incident sont dispersées entre logs réseau, CRM, historique des tickets et catalogues de produits. Cette fragmentation oblige les équipes de support à consulter manuellement plusieurs outils.

\paragraph{Dépendance à l'expertise humaine :}
Le diagnostic repose largement sur l'expérience individuelle des techniciens. Le savoir-faire est difficile à formaliser et à transmettre.

\paragraph{Temps de résolution et risque d'erreur :}
La consultation manuelle de sources hétérogènes engendre des temps de diagnostic longs et un risque d'erreur d'interprétation.

\paragraph{Systèmes legacy :}
Le SI CCU s'appuie sur des composants hérités dont les interfaces varient. Toute solution doit s'intégrer sans perturber ces systèmes existants.

\subsection{Besoins non fonctionnels}
Le système doit satisfaire les besoins non fonctionnels suivants :

\begin{itemize}
    \setlength\itemsep{0.1em}
    \setlength\parskip{0pt}
    \setlength\parsep{0pt}
    \item \textbf{Sécurité :} aucune action corrective automatique sur un système réel.
    \item \textbf{Protection des données :} filtrage des PII avant envoi externe.
    \item \textbf{Performance :} diagnostic en quelques secondes.
    \item \textbf{Traçabilité :} journal d'audit de chaque exécution.
    \item \textbf{Extensibilité :} ajout facilité de nouveaux agents ou sources.
    \item \textbf{Testabilité :} composants testables unitairement et en intégration.
\end{itemize}

\section{Conception de l'architecture}

\subsection{Vue d'ensemble du pipeline}
L'architecture repose sur un graphe d'état implémenté avec \textbf{LangGraph}. Le flux de traitement d'un incident suit le cheminement suivant : intake, collecte parallèle des sources, raisonnement sur la cause racine, gestion du ticket, explication de la remédiation, guardrail de contenu, génération du rapport, puis notification.

\subsection{Architecture générale}
Le système se décompose en cinq grands composants :

\begin{itemize}
    \setlength\itemsep{0.1em}
    \setlength\parskip{0pt}
    \setlength\parsep{0pt}
    \item \textbf{Interface et API} : chatbot Streamlit et API REST FastAPI.
    \item \textbf{Orchestrateur LangGraph} : pipeline agentique en graphe d'état.
    \item \textbf{Agents spécialisés} : intake, collecteurs, raisonnement, ticket manager, remédiation, guardrail, report generator, notifier.
    \item \textbf{Sources de données} : logs mockés, CRM mock, graphe Neo4j.
    \item \textbf{Services externes} : Zammad, MailHog, Docker Compose.
\end{itemize}

\subsection{Communication entre les composants}
Les communications s'effectuent via l'API REST FastAPI. Le client envoie un payload JSON décrivant l'incident. L'orchestrateur invoque les agents, met à jour l'état partagé et retourne un flux d'événements Server-Sent Events (SSE) pour le suivi en temps réel.

\subsection{Contraintes et index vectoriel}
Le fichier \texttt{graph/schema.cypher} définit les contraintes d'unicité sur chaque entité et crée un index vectoriel sur les embeddings des tickets. Cet index permet d'effectuer une recherche de similarité cosine nativement dans Neo4j. Le provider Ollama avec le modèle \texttt{mxbai-embed-large:latest} est utilisé par défaut pour produire ces embeddings.

\section{Workflow des agents}
Le workflow est modélisé par un graphe d'état LangGraph. La classe \texttt{DiagnosticPipeline} construit le graphe en déclarant les nœuds et les arêtes. Le nœud \texttt{collectors} encapsule le parallélisme des trois agents collecteurs (logs, contexte client, tickets similaires). Après la collecte, l'agent de cause racine corrèle les sources, le ticket manager rattache ou crée le ticket, le remédiateur rédige une fiche informative, le guardrail filtre les PII, le report generator produit le PDF, et le notifier envoie l'email.

\section{Workflow RAG}
La recherche GraphRAG combine deux mécanismes :

\begin{enumerate}
    \item \textbf{Recherche vectorielle} : vectorisation de l'incident courant, puis recherche cosine dans Neo4j.
    \item \textbf{Filtre de proximité de graphe} : conservation des tickets liés au même produit ou type de commande.
\end{enumerate}

Cette approche améliore la précision par rapport à une simple recherche sémantique en intégrant la structure relationnelle du graphe.
