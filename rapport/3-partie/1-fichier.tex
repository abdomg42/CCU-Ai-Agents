\section*{Introduction}
Le Chapitre 2 a posé le cadre conceptuel et architectural de la migration : analyse des systèmes sources, conception du pipeline ETL, stratégie de validation par Dry Runs et politique de gestion des risques. La réalisation s'articule en deux temps distincts, reflétant l'organisation en jalons du projet :
\begin{itemize}
	\item Les Jalons 1, 2 et 3 portent sur la migration de GAIA, le système d'inventaire réseau existant, vers Ni2 Unified Inventory. Cette phase recouvre cinq thèmes d'inventaire traités séquentiellement : \textbf{Locations}, \textbf{Services \& Customers}, \textbf{Device global}, \textbf{Devices Cuivre} et \textbf{Devices MSAN}.

Cette phase comprend la rétro-ingénierie de la base de données, l'identification et le filtrage des tables sources, la conception des scripts de transformation, l'import en environnement DEV, la validation de la réconciliation et les tests d'intégration de bout en bout avec les systèmes Façade et CRM.
\end{itemize}

\section{Migration GAIA vers Ni2}
La base GAIA est une base Oracle multi-schémas structurée autour de cinq familles d'objets : emplacements géographiques, clients et services, équipements physiques, connectivité physique et connectivité logique. Son modèle est documenté et les scripts de migration ont été produits en collaboration avec l'équipe Inetum sous supervision du chef de projet Ni2. \\
Le pipeline ETL repose sur le framework Java propriétaire Ni2 (classes AbstractSampleScript et ImportScriptTools), décrit au Chapitre 2. Chaque script produit un ou plusieurs fichiers CSV pivot qui sont ensuite chargés dans Ni2 via le mécanisme SQL Sync en respectant les sept phases d'import séquentielles.

Le passage du modèle théorique aux données exploitables a nécessité le développement d'une suite de scripts SQL complexes. Pour respecter l'intégrité référentielle de Ni2, ces scripts ont été conçus pour être exécutés selon un ordre séquentiel strict (comme le montre le préfixe 01, 02... dans leurs noms), permettant de créer les objets parents avant leurs dépendances.
Les scripts d'extraction SQL ont été développés pour ce thème, correspondant aux niveaux hiérarchiques du modèle Ni2 :
\paragraph{Script 1 --- Extraction des entités géographiques (\texttt{GAI\_1LOC\_...\_SousReseau.sql}) :}
Ce script prépare le format pivot Ni2 en utilisant la nomenclature requise par le framework de migration. Comme l'illustre l'extrait en Figure \ref{fig:script_sql_1}, la requête traite trois couches de données simultanément :
\begin{itemize}
    \setlength\itemsep{0.1em}
    \item[---] \textbf{L’Instance (Préfixe I.) :} Mapping des attributs de base (Nom, Acronyme, Statut).
    \item[---] \textbf{Le Catalogue (Préfixe T.) :} Rattachement au type de modèle défini dans Ni2.
    \item[---] \textbf{La Relation (Préfixe REL.) :} Création dynamique des liens de parenté (par exemple entre le Pays et le Sous-Réseau) via l'opérateur de jointure.
\end{itemize}

\textbf{Expertise technique :} L'utilisation de l'identifiant \textit{UniversalId} (construit par concaténation) assure la traçabilité de l'objet depuis le système source GAIA jusqu'à la cible.

\subsubsection{Modélisation des objets relatifs aux « Clients » et « Services »}
La modélisation des Services et Clients constitue le pivot logique du nouvel inventaire, car elle assure la convergence entre le référentiel commercial et l’infrastructure technique. Comme l’illustre la planche de modélisation ci-après, cette architecture repose sur une chaîne de dépendances rigoureuse allant de l'entité contractuelle jusqu'à la ressource terminale.\\
D’un côté, le modèle définit le parcours du client (Actor) qui consomme un Produit (Service Package), lequel se décline en Services métiers (Business) et en Accès techniques (Technical). Cette structure permet de lier dynamiquement un abonné à son emplacement physique (Site Client) via la relation AllocatedTo.\\
D’un autre côté, une attention particulière est portée à la gestion de la numérotation. Le modèle introduit le concept de "Parent ND", représentant les boîtes à numéros au niveau des répartiteurs (ONU). Cette hiérarchie technique, segmentée par type de boîte (ND, NE) et par autocommutateur (CTB, CTD), est cruciale pour le système : elle permet de gérer l'inventaire des numéros (libres ou assignés) et d'automatiser leur attribution lors des prises de commandes. Cette double approche garantit une traçabilité totale, permettant à l’opérateur télécom de connaître instantanément quelle ressource technique supporte quel service client, et à quelle adresse précise.

\subsubsection{Scripts développés}
Les scripts ont été développés pour ce thème, dans l'ordre strict des dépendances :
\begin{itemize}
    \item \textbf{Script 1 — GAI\_2CUS...\_Customer.sql :} extraction des clients GAIA avec leurs attributs d'identification (nom, référence externe, catégorie B2B/B2C, document d'identification). L'Universal Id est alimenté par la référence client GAIA pour permettre la réconciliation lors de la migration CRM (Jalon 4). Les attributs non modifiables (Alias, Statut, Catégorie, Référence Client Externe) sont marqués en read-only dans Ni2 car ils seront ultérieurement synchronisés depuis le CRM.
    \item \textbf{Script 2 — GAI\_2CUS...\_ServicePackage.sql :} extraction des produits et services actifs GAIA. La difficulté technique réside dans la correspondance entre la nomenclature de l'offre GAIA (codes produits propriétaires) et la classification Ni2 Package/Business/Technical. Une table de correspondance (lookup table) a été construite avec le fonctionnel de l'opérateur telecom pour valider les associations.
    \item \textbf{Script 3 — GAI\_2CUS...\_ParentND.sql :} extraction des boîtes à numéros (ND Parents) depuis le référentiel GAIA. Chaque ND Parent est caractérisé par son TypeDeBoite (ND ou NE), son NumDeBoite (CBN), son Produit associé, son Autocommutateur (CTD ou CTB) et son Site ONU de rattachement. Ces attributs sont définis dans le LLD fonctionnel dans la liste des attributs de l'objet ND Parent.
    \item \textbf{Script 4 — GAI\_2CUS...\_AssignedND.sql :} extraction des Numéros de Désignation assignés ou libres. Chaque ND est rattaché à son ND Parent (relation Documents) et, pour les ND Assignés, à un Produit via la relation AllocatedTo. Le statut Assigné/Libre est calculé depuis GAIA selon la présence ou l'absence d'un contrat actif associé.
\end{itemize}

\subsubsection{Résultats et validation IHM}
La validation du thème Services \& Customers a représenté l'étape la plus complexe de la migration GAIA, avec le traitement de plus de 35 000 packages de services et 50 000 numéros de désignation. Comme le montre le suivi des tests unitaires, les comptages effectués via des requêtes NQL ont permis de valider un Perfect Match sur l'essentiel des instances clients et produits.\\
Toutefois, la phase de réconciliation a mis en lumière des incohérences critiques au sein du système legacy, notamment concernant les 7 551 numéros de désignation (ND) orphelins. Ces numéros ne disposaient d'aucune référence de répartiteur (ONU) ou de boîte (CBN) exploitable dans GAIA, rendant impossible leur raccordement automatique à un "Parent ND" dans Ni2. De même, l'analyse a révélé des cas de partage d'adresses entre plusieurs clients (27 adresses partagées par deux clients, 3 par trois clients), nécessitant un arbitrage pour garantir l'unicité de la localisation technique.\\
Malgré ces écarts inhérents à la qualité des données sources, l'implémentation de règles de nettoyage et l'utilisation de l'Universal ID (basé sur la référence GAIA) ont permis d'aboutir à un inventaire commercial parfaitement aligné avec l'inventaire technique, sécurisant ainsi les futurs processus de facturation et de support client.

\section{Rétro-ingénierie et Migration CRM}
Le Jalon 4 constitue le défi technique le plus structurant de ce stage. À la différence de GAIA, dont le modèle est documenté et maîtrisé par l'équipe Inetum, le CRM de l'opérateur telecom repose sur une base MSSQL de plus de 900 tables construite de façon incrémentale, sans documentation formelle. L'enjeu dépasse la simple extraction de données : il s'agit de reconstruire, par rétro-ingénierie, une
connaissance complète du modèle de données avant de pouvoir concevoir le moindre script
d'extraction. Cette section restitue l'intégralité de la démarche conduite en responsabilité propre.

\subsection{Investigation et Rétro-ingénierie du CRM}
En l'absence de toute documentation de la base MSSQL, la rétro-ingénierie a été conduite selon trois
axes successifs, chacun conditionnant la crédibilité du suivant.
\paragraph{Exploration et identification des entités critiques}: \\
La première étape a consisté à cartographier les 900+ tables pour en extraire les entités
fonctionnellement pertinentes pour Ni2 (Clients, Adresses, Contacts). La difficulté principale ne résidait
pas dans le nombre de tables mais dans leur contenu : les colonnes discriminantes sont codifiées sous
forme de valeurs numériques sans libellé explicite, rendant toute interprétation directe impossible.
L'un des défis majeurs a été de traduire les valeurs numériques brutes en règles de gestion métier. Deux filtres critiques ont été identifiés :
\begin{itemize}
    \item \textbf{crm\_systemedebillingcode = 171060002} : Ce code identifie les abonnements actifs et facturables. L'information n'étant pas documentée, j'ai dû développer des scripts de recherche transversaux pour localiser les tables de métadonnées. Cette investigation a permis de remonter jusqu'à la table système \textbf{StringMap}, qui fait office de dictionnaire de libellés pour le CRM Microsoft Dynamics. Ce n'est qu'après l'analyse croisée de cette table et la confirmation des équipes de l'opérateur telecom que le mapping a pu être validé.
    \item \textbf{statecode = 0} : Ce filtre permet d'isoler les enregistrements "Actifs" (non supprimés ou archivés). Bien que standard dans la convention de Microsoft Dynamics CRM, sa validation a nécessité une analyse sémantique du contenu pour confirmer que les données correspondantes étaient bien celles exploitées en production.
\end{itemize}

\paragraph{Stratégie de pivot en collaboration avec l'équipe Comarch}\\
Pour concentrer les données utiles et simplifier l'interface avec le pipeline Ni2, une collaboration avec
l'équipe projet Comarch a abouti à la création de trois tables pivots dédiées à la migration :

\subsection{ Développement des Scripts T-SQL et Fichier de Mapping}
Avant tout développement script, un fichier Excel de mapping a été élaboré pour formaliser la
correspondance champ par champ entre le modèle CRM et les attributs Ni2 définis dans le LLD
fonctionnel. Ce document de référence a servi de contrat entre les
équipes techniques et fonctionnelles tout au long du Jalon 4. Trois scripts T-SQL ont ensuite été
développés, chacun implémentant des règles de gestion spécifiques :

\paragraph{\textbf{Script 1 — Adresses} }\\
Ce script reconstruit une adresse normalisée à partir de champs fragmentés dans le CRM (voie, bâtiment, escalier, étage). La fonction CONCAT\_WS assemble les composantes disponibles en ignorant automatiquement les valeurs NULL, produisant une valeur Full Address conforme à la règle de calcul du LLD : \\ 
\textbf{CONCAT\_WS(', ', voie, batiment, escalier, etage, quartier, ville) -> Full Address Ni2}\\
Un identifiant universel (Universal Id) est calculé sur la clé primaire CRM pour garantir la déduplication lors de la réconciliation avec les adresses déjà importées depuis GAIA.
    
\paragraph{\textbf{Script 2 — Clients} }\\
Ce script gère la distinction B2C/ B2B via le champ discriminant CRM, puis construit dynamiquement la relation Consumes entre le Client et son Adresse dans Ni2 via l'Universal Id. Les filtres de qualité suivants sont appliqués de façon systématique : \\ 
\textbf{\textit{crm\_systemedebillingcode = 171060002 -- abonnements facturables uniquement}} \\ 
\textbf{\textit{statecode = 0 -- enregistrements actifs (non archivés)}} \\ 
Ces filtres, définis après concertation avec les équipes de l'opérateur telecom, garantissent que seules les données commercialement actives et techniquement cohérentes sont injectées dans Ni2, une règle de gestion documentée dans le fichier de mapping Excel.
    
\paragraph{\textbf{Script 3 — Contacts} }\\
Ce script implémente une logique de rôles fonctionnels via des structures CASE WHEN pour catégoriser dynamiquement chaque contact et alimenter les responsabilités dans Ni2 : 
    \begin{lstlisting}[language=SQL, caption={Transformation des rôles contacts}]
        CASE crm_role 
            WHEN 'PF'  THEN 'Point focal'
            WHEN 'MAN' THEN 'Mandataire'
            WHEN 'REP' THEN 'Représentant'
            ELSE 'Contact' 
        END AS "REL2.ContactType"
    \end{lstlisting}

\subsection{Validation, Tests Unitaires et Dossier de Recette}
La phase de validation a suivi un protocole en trois niveaux, du plus technique au plus fonctionnel,
aboutissant à la production d'un livrable formel.

\paragraph{Analyse des logs et traitement des rejets}\\
Après chaque import, les fichiers de log SQL Sync sont analysés systématiquement pour en extraire
les lignes ERROR et WARN. Pour chaque rejet, la cause est catégorisée (contrainte d'intégrité
référentielle, valeur de picklist non reconnue, objet parent manquant, doublon sur clé unique) et traitée
par correction dans le script ou dans les tables pivots, avant re-run sur les enregistrements en erreur
uniquement.

\paragraph{Tests unitaires sur l'IHM Ni2} \\
Une fois l'import stabilisé, une vérification visuelle est conduite directement dans l'interface Ni2 sur un
échantillon représentatif de clients. Les points de contrôle couvrent :
\begin{itemize}
    \item Création correcte de l'objet Client (Actor/Customer) avec l'ensemble de ses attributs d'identification, y compris les champs non modifiables récupérés depuis le CRM (Alias, Catégorie, Référence Client Externe)
    \item  Rattachement correct de l'adresse au client via la relation Consumes — vérification que la Full Address concaténée est cohérente avec les données sources CRM.
    \item  Effectivité de la réconciliation CRM « GAIA : un client présent dans les deux sources doit apparaître une seule fois dans Ni2, avec ses attributs techniques (GAIA) et commerciaux (CRM) correctement fusionnés.
    \item Cohérence des rôles de contacts : vérification que les valeurs Point focal, Mandataire, Représentant sont correctement portées dans les champs de responsabilité Ni2
\end{itemize}

\subsection{Enseignements et points d'amélioration}
La réalisation de ces jalons a mis en évidence plusieurs facteurs clés de succès pour un projet de migration de données télécom :

\begin{itemize}
    \item[---] \textbf{Qualité des données sources :} C'est le facteur de risque principal. Les taux de rejet proviennent quasi exclusivement d'incohérences préexistantes (adresses incomplètes, numéros orphelins). L'investissement dans l'analyse de données en amont est donc crucial.
    \item[---] \textbf{Stratégie de clé universelle :} L'\textit{Universal Id} de Ni2 s'est révélé être le mécanisme le plus fiable pour assurer la réconciliation inter-systèmes (GAIA vs CRM) sans générer de doublons.
    \item[---] \textbf{Anticipation des tests d'intégration :} La détection d'anomalies lors des tests finaux montre que l'exécution de smoke test dès les premiers Dry Runs aurait permis un gain de temps significatif.
    \item[---] \textbf{Valorisation de la rétro-ingénierie :} La connaissance acquise sur le modèle CRM non documenté constitue désormais un actif immatériel majeur pour l'entreprise, réutilisable pour la maintenance future du système.
\end{itemize}
