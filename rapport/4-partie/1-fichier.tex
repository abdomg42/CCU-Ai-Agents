\section{Scénarios d'utilisation}

\subsection{Scénario 1 : Coupure fibre optique}
Un opérateur reçoit l'incident suivant :

\begin{fquote}
Client acc-12345, service svc-fiber-12345, commande ord-2026-001. Coupure Internet fibre.
\end{fquote}

Le pipeline exécute successivement les étapes suivantes :

\begin{enumerate}
    \item \textbf{Intake} : extraction de \texttt{customer\_id=acc-12345}, \texttt{service\_id=svc-fiber-12345}, \texttt{order\_id=ord-2026-001}, type \texttt{fibre}, priorité \texttt{P2}.
    \item \textbf{Collecte} : logs OLT, contexte client CRM et tickets similaires de coupure fibre en parallèle.
    \item \textbf{Root cause} : cause racine \texttt{Perte de signal fibre optique} avec confiance moyenne ou forte.
    \item \textbf{Ticket manager} : création du ticket \texttt{TICK-CCU-XXXX}.
    \item \textbf{Remediation} : proposition d'actions informatives (vérification de la paire, test optique).
    \item \textbf{Guardrail} : vérification PII.
    \item \textbf{Report generator} : génération du PDF \texttt{INC-CCU-XXXX.pdf}.
    \item \textbf{Notifier} : envoi d'un email et ajout d'une note interne dans Zammad.
\end{enumerate}

\subsection{Observation des résultats}
La démonstration peut être observée à plusieurs endroits :

\begin{itemize}

    \item \textbf{Streamlit} : affichage de la trace agent et du lien de téléchargement du rapport.

\section{Performances}

\subsection{Tests automatisés}
Le projet utilise \textbf{pytest} avec le mode asynchrone activé. Les tests couvrent le parsing d'incident, la récupération du contexte client, le filtrage PII, l'exécution complète du pipeline, l'ingestion Neo4j et la recherche GraphRAG.

\subsection{Golden incidents}
Le répertoire \texttt{evaluation/golden\_incidents/} contient les cas de test attendus. Le runner \texttt{eval\_runner.py} rejoue ces incidents, compare les résultats aux attentes et produit un rapport pass/fail avec une accuracy globale.

\subsection{Métriques de performance}
En mode mock, le pipeline s'exécute en quelques secondes. Le temps de réponse dépend principalement de la latence d'Ollama lorsque le LLM est activé, du temps de recherche vectorielle dans Neo4j et de la génération du PDF.

\section{Avantages}
La solution apporte plusieurs avantages par rapport au diagnostic manuel :

\begin{itemize}
    \setlength\itemsep{0.1em}
    \setlength\parskip{0pt}
    \setlength\parsep{0pt}
    \item \textbf{Gain de temps} : agrégation automatique des sources pertinentes.
    \item \textbf{Fiabilisation} : corrélation structurée et raisonnement guidé par les données.
    \item \textbf{Capitalisation} : réutilisation des tickets historiques via le graphe Neo4j.
    \item \textbf{Sécurité} : aucune action corrective automatique et filtrage des PII.
    \item \textbf{Traçabilité} : journal d'audit de chaque exécution.
    \item \textbf{Industrialisation} : API REST, tests automatisés et déploiement Docker.
\end{itemize}

\section{Limites}
Certaines limites demeurent et constituent des axes d'amélioration :

\begin{itemize}
    \setlength\itemsep{0.1em}
    \setlength\parskip{0pt}
    \setlength\parsep{0pt}
    \item \textbf{Données mockées} : le système s'appuie sur des données simulées, ce qui limite la généralisation à un environnement de production réel.
    \item \textbf{LLM local} : les performances du modèle local peuvent être inférieures à celles d'un modèle cloud pour des cas complexes.
    \item \textbf{Mode mock déterministe} : en mode \texttt{MOCK\_LLM=true}, le raisonnement est entièrement déterministe et ne bénéficie pas de la créativité du LLM.
    \item \textbf{Couverture des cas} : le jeu de golden incidents est limité et devrait être enrichi.
\end{itemize}
