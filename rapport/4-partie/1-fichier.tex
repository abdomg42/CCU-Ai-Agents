\section*{Introduction}
Ce chapitre présente la stratégie de validation du projet, les tests automatisés mis en place, le déploiement via Docker Compose, ainsi qu'un scénario de démonstration de bout en bout.

\section{Stratégie de test}

\subsection{Tests unitaires et d'intégration}
Le projet utilise \textbf{pytest} pour valider le fonctionnement des agents, de l'ingestion Neo4j et des requêtes GraphRAG. La configuration de pytest est définie dans \texttt{pyproject.toml} avec le mode asynchrone activé.

\begin{lstlisting}[language=Python, caption={Configuration pytest dans pyproject.toml}]
[tool.pytest.ini_options]
testpaths = ["tests"]
pythonpath = ["."]
asyncio_mode = "auto"
\end{lstlisting}

Les tests couvrent les domaines suivants :

\begin{itemize}
    \setlength\itemsep{0.1em}
    \setlength\parskip{0pt}
    \setlength\parsep{0pt}
    \item \textbf{Intake} : validation du parsing heuristique.
    \item \textbf{Contexte} : récupération du contexte client.
    \item \textbf{Guardrail} : vérification du filtrage PII.
    \item \textbf{Pipeline} : exécution complète du graphe en mode mock.
    \item \textbf{Graph ingestion} : compteurs de nœuds et relations après seed.
    \item \textbf{GraphRAG} : recherche de tickets similaires.
\end{itemize}

\subsection{Tests Neo4j}
Les tests \texttt{test\_graph\_ingestion.py} et \texttt{test\_rag.py} nécessitent une instance Neo4j accessible. Ils seedent automatiquement le graphe et vérifient :

\begin{itemize}
    \setlength\itemsep{0.1em}
    \setlength\parskip{0pt}
    \setlength\parsep{0pt}
    \item La création correcte des nœuds \texttt{Client}, \texttt{Subscription}, \texttt{Order}, \texttt{Product}, \texttt{Ticket} et \texttt{LogEvent}.
    \item L'existence des relations attendues.
    \item Le fonctionnement de la recherche vectorielle avec le seuil de similarité configuré.
\end{itemize}

\subsection{Golden incidents}
Le répertoire \texttt{evaluation/golden\_incidents/} contient un ensemble de cas de test attendus. Le runner \texttt{eval\_runner.py} rejoue ces incidents, compare les résultats aux attentes et produit un rapport pass/fail avec une accuracy globale. Le processus retourne un code de sortie 0 si tous les cas passent.

\section{Déploiement}

\subsection{Docker Compose}
Le fichier \texttt{docker/docker-compose.yml} permet de démarrer l'ensemble des services : API FastAPI, Neo4j, Zammad, Mailhog, Splunk et Prism. Cette infrastructure facilite la démonstration de bout en bout sans dépendre d'un environnement externe.

\begin{lstlisting}[language=bash, caption={Démarrage de l'infrastructure}]
cd docker
docker compose up --build
\end{lstlisting}

L'API est alors accessible sur \texttt{http://127.0.0.1:8000}, Neo4j sur \texttt{http://localhost:7474}, Zammad sur \texttt{http://localhost:3000} et Mailhog sur \texttt{http://localhost:8025}.

\subsection{Seed des données}
Une fois l'infrastructure démarrée, les commandes suivantes permettent de peupler la base Neo4j et Zammad :

\begin{lstlisting}[language=bash, caption={Seed des données}]
make seed
make seed-tickets
make seed-zammad
\end{lstlisting}

\section{Scénario de démonstration}

\subsection{Description du cas}
Un opérateur reçoit l'incident suivant, exprimé en langage naturel :

\begin{fquote}
Client acc-12345, service svc-fiber-12345, commande ord-2026-001. Coupure Internet fibre.
\end{fquote}

\subsection{Déroulement du diagnostic}
Le pipeline exécute successivement les étapes suivantes :

\begin{enumerate}
    \item \textbf{Intake} : extraction de \texttt{customer\_id=acc-12345}, \texttt{service\_id=svc-fiber-12345}, \texttt{order\_id=ord-2026-001}, type \texttt{fibre}, priorité \texttt{P2}.
    \item \textbf{Collecte} : logs OLT, contexte client CRM et tickets similaires de coupure fibre en parallèle.
    \item \textbf{Root cause} : cause racine \texttt{Perte de signal fibre optique} avec confiance moyenne ou forte.
    \item \textbf{Ticket manager} : création du ticket \texttt{TICK-CCU-XXXX}.
    \item \textbf{Remediation} : proposition d'actions informatives (vérification de la paire, test optique).
    \item \textbf{Guardrail} : vérification PII.
    \item \textbf{Report generator} : génération du PDF \texttt{INC-CCU-XXXX.pdf}.
    \item \textbf{Notifier} : envoi d'un email et ajout d'une note interne dans Zammad.
\end{enumerate}

\subsection{Observation des résultats}
La démonstration peut être observée à plusieurs endroits :

\begin{itemize}
    \setlength\itemsep{0.1em}
    \setlength\parskip{0pt}
    \setlength\parsep{0pt}
    \item \textbf{Chatbot Next.js} : affichage de la trace agent et du lien de téléchargement du rapport.
    \item \textbf{Mailhog} : réception de l'email avec le PDF en pièce jointe.
    \item \textbf{Zammad} : ticket créé avec une note interne indiquant l'envoi du rapport.
    \item \textbf{Neo4j Browser} : visualisation des nœuds et relations du graphe avec le style GRASS fourni.
\end{itemize}

\section*{Conclusion}
Ce chapitre a présenté la stratégie de validation du projet, fondée sur des tests automatisés et des cas golden incidents, ainsi que le déploiement via Docker Compose et un scénario de démonstration de bout en bout.
